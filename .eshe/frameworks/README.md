# Framework library

The initial library covers three requested families: [software architecture](architecture.md), [agent decision systems](agents.md), and [product/design systems](product-design.md).

The agent family also includes [workflow-system decision cards](workflow-systems.md), derived from the 2026-09-24 comparison of Spec Kit, OpenSpec, GSD, Superpowers, BMAD and Kiro. Select a card for a concrete process gap; these are not additional products to install.

These are selective adaptations checked against primary sources on 2026-09-24. They are not verbatim transcripts, a ranking of “best” designs, exhaustive reference manuals, or automatic mandates. Eshe-specific gates and proof requirements are our synthesis of those sources and the local skills.

## Card contract

Each imported framework must answer: when it applies, what question it resolves, what artifact it produces, what evidence could reject the decision, and when not to use it. Preserve source/author/date and distinguish source claims from Eshe adaptations.

When importing another pattern, first name the unresolved project decision. If no decision changes, do not add a card. Version-specific API, platform or regulatory details must be verified when used. Add a decision record before changing an established architecture or design authority.

## How the library enters execution

- Architecture flow selects ownership, decomposition, consistency or compatibility cards.
- Bootstrap/interview selects discovery and problem-definition tools only for missing decisions.
- UI flow selects research, kit and experience guidance according to tier.
- Lifecycle and future runner use explicit state/gate concepts.
- The current task loads only selected cards. The rest remains reference material.
